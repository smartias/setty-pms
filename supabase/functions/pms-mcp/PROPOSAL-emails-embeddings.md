# Proposal: meaning-based search for the filed email log

Status: PROPOSED (2026-10-20). Nothing built. Written the day the CA items
experiment passed (`EXPERIMENT-ca-items-semantic.md`: hybrid found 9 of 10,
keyword 2 of 10, nothing lost), because the same model, the same job and the
same pass rule transfer to emails with little new code. This is the "later"
that `PROPOSAL-ca-items-embeddings.md` put emails on.

## The ask, in one paragraph

Give `search_emails` the same meaning-based ranking the RFI and submittal
search now has, so "the exchange about the chiller disconnect" finds the
thread even when nobody wrote those words. Store one 384-number embedding per
filed email next to the row, for every project in the PMS (design, CA,
completed, on hold), fill it with the same one-minute job pattern,
fuse it with today's keyword ranking in the search function, and keep it OFF
behind a flag until a ten-question experiment on real emails passes the same
rule the CA search had to pass. Two things make email different from RFIs
and will shape the work: the log holds only what people file with the Outlook
add-in, and threads repeat the same text many times.

## What exists today

- `pms_project_emails`: one row per filed email, written by the PMS on every
  add-in save (`saveProjectEmailRowFromPMS` in `SettyPMS.html`). Columns that
  matter here: `record_id`, `project_id`, `conversation_id`, `subject`,
  `from_name`, `from_address`, `email_date`, `body_text`, `preview`,
  `attachment_names`, `sp_folder_url`.
- Counts on 2026-10-19: **21,017 emails, 20,701 with a body**.
- Keyword search: the connector's `search_emails` tool calls the database
  function `search_project_emails(q, proj, lim)`, which returns ranked rows;
  `sender` and `direction` filters are applied after. **The function's
  definition is not in the repository**, it was created directly in the
  database. Step 0 below fixes that before anything touches it.
- The embedding model (`gte-small`, inside the edge runtime, nothing leaves
  Supabase), `runEmbedPass` (the CPU-sized embed loop with tests) and the
  one-minute route pattern all exist from the CA work.

## What is different about email

1. **Coverage.** Only mail filed with the add-in is in the log. A better
   ranking over an incomplete log can make "nothing came up" sound like
   "nothing exists". The pre-check below measures the gap per project, and
   the answer should keep saying, as it does today, that the log only holds
   filed mail.
2. **Threads repeat.** The portal census on 2026-10-19 showed the same
   subject filed ten or more times as RE:/FW: replies. Each reply quotes the
   ones before it, so their embeddings will be near-identical and a single
   thread would fill the whole top five. The search must collapse results by
   `conversation_id` (or by normalized subject when it is null) and show one
   row per thread, newest message, with the thread's count.
3. **Noise in the body.** Signatures, legal footers, portal boilerplate
   ("Notification generated by Newforma", "To unsubscribe"), and the quoted
   history under each reply. Outlook puts the newest text first and the
   quoted history below it, so capping the embedded text at the first 1,500
   characters keeps mostly the new message. A small cleaning function strips
   the known footers and anything after the first "From:" / "-----Original
   Message-----" / "On … wrote:" line.
4. **Scale.** 21,017 rows at the measured 5 rows a minute is about 70 hours
   of one-minute calls, roughly three days. A second cron entry offset by 30
   seconds halves that; Supabase's cron accepts a `30 seconds` schedule.
   Storage is about 32 MB. An exact scan over 21,000 vectors should answer
   in tens of milliseconds; measure after the backfill and add an HNSW index
   only if a search exceeds about 300 ms.

## The proposal, in order

### Step 0. Capture the current email search function (half a day)

Write the live `search_project_emails` definition into a migration file so
the repository holds it and the hybrid version is a reviewable diff. Nothing
changes in behaviour. (`pg_get_functiondef` in the SQL editor gives the text.)

### Step 1. Migration (one day)

- `alter table pms_project_emails add column embedding extensions.vector(384),
  embedded_at, embedded_hash`.
- `pms_emails_embed_text(subject, body_text)`: the cleaning above, capped at
  1,500 characters.
- `pms_emails_to_embed(p_limit)` and `pms_emails_store_embeddings(p_rows)`:
  the same shape as the CA helpers, hash-guarded.
- `search_project_emails(q, proj, lim, p_embedding default null,
  p_min_similarity default 0.75)`: keyword list and nearest-vector list fused
  by reciprocal rank, exactly as `search_ca_items` does, then **collapsed to
  one row per thread** with `thread_count` and the newest `record_id`.
  Behaviour with no embedding is unchanged, so this can ship first.
- Local test file like `ca-items-local-test.sql`, including a thread of three
  replies that must come back as one row.

### Step 2. Connector (one day)

- `POST /pms-mcp/admin/emails-embed`: `runEmbedPass` with the two email RPCs
  injected. Same auth, same sizing (20 rows a call, store every 5, 1.5 s
  deadline), scheduled once a minute next to `pms-ca-items-embed`.
- `search_emails`: embed a prose query when the flag `EMAILS_SEMANTIC=1` is
  set (OFF by default until the experiment), pass it to the function, report
  `searchMode` and `threadCount`. `summarize_project_emails` and `read_email`
  are untouched.
- Tests for the cleaning rules in the pure module, on real filed emails with
  names trimmed: a Newforma forward, a Procore notification, a plain reply
  with a signature, a three-deep quoted thread.

### Step 3. Backfill and the experiment (three days of wall time, one hour of work)

- Schedule the job, wait for coverage (`embedded = rows with a body`,
  `queued = 0`), measure search latency.
- Ten questions about emails, written before searching, each with an
  expected thread found by browsing a project's email tab, not by searching.
  Spread them across phases: at least three from design-phase projects and
  at least three from CA, so the result is not a CA-only result.
  Same sheet layout and the same rule: **Gained 3 or more AND Lost 0**, each
  question run with the flag off and on, limit 5, firm-wide. One extra check:
  no thread appears twice in any hybrid top five.
- Pass: flag defaults on, as the CA search does now. Fail: one PR removes the
  column, the helpers, the parameters, the route and the cron entry.

## Pre-check before any of it (one query)

The embedding column and the hybrid search cover **every row in
`pms_project_emails`, for every project**, whatever its status. CA projects
are not special here: a design-phase project's mail about a code question or
an owner decision is searched the same way. So the pre-check looks at the
whole firm, not the CA list.

How much of each project's mail is actually filed? Run in the Supabase SQL
editor (one row per project, active statuses first):

```sql
select p.project->>'status' as status,
       p.project->>'projectNumber' as project, p.project->>'name' as name,
       count(e.record_id) as filed_emails,
       max(e.email_date)::date as newest_filed
from public.pms_projects p
left join public.pms_project_emails e on e.project_id = p.id
group by 1, 2, 3
order by (p.project->>'status' in ('Completed','Cancelled','Lost')), 4 desc;
```

And the one-line summary by status, which is the number that decides:

```sql
select p.project->>'status' as status,
       count(*) as projects,
       count(*) filter (where e.n > 0) as with_filed_mail,
       coalesce(sum(e.n), 0) as filed_emails
from public.pms_projects p
left join (select project_id, count(*) as n
           from public.pms_project_emails group by project_id) e
  on e.project_id = p.id
group by 1 order by 4 desc;
```

Projects with few or no filed emails are where a meaning-based search would
look confident and be wrong. If most active projects (In Progress, In for
Review, Top Priority, In Construction Administration) are near zero, the
filing habit is the thing to fix first and this proposal waits. Completed and
Cancelled projects still get embedded; old mail is often exactly what a
"have we seen this before" question needs.

## Risks and what limits them

- **Confidential content.** Embeddings are computed and stored inside the
  firm's Supabase project by the runtime's own model. No text is sent to any
  outside service. The embedding column is readable only through the search
  function, like the CA one.
- **A thread swamps the results.** The collapse by conversation is in the
  function, not the connector, so every caller gets it.
- **Quoted history dominates the embedding.** The 1,500-character cap on the
  newest-first body limits it; the cleaning strips the rest. The test fixtures
  make this visible.
- **Backfill cost.** Three days of one-minute calls at a few hundred
  milliseconds of CPU each is well inside the free allowance; the CA job has
  run the same way since 2026-10-19.
- **It does not solve coverage.** It will not, and the answer text keeps
  saying so. The portal-intake proposal and filing discipline are the fixes
  for that.
